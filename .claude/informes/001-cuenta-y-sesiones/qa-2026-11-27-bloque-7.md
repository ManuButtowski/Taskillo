## Hallazgos
1. **[grave]** El script remoto del despliegue se corta tras `docker compose run` y el job termina en verde sin ejecutar `up -d` (deploy.yml, paso "Pull, migraciones y up -d").
   - Frontera: workflow -> VPS. El script se envía por `ssh ... bash -s` leyendo de stdin; `docker compose run` sin `-T` ni redirección conserva stdin abierto y consume el resto del script.
   - Reproducción (simulada en local con el mismo patrón, el compose de producción y una imagen local): `cat remoto.sh | bash -s` con `set -euo pipefail`, `$dc run --rm api echo OK` y después `echo "PASO_DESPUES"`.
   - Esperado: se ejecuta el `echo` posterior (en el workflow, `up -d --remove-orphans` y `docker image prune -f`).
   - Obtenido: el contenedor corre, el `echo` posterior **no se ejecuta** y el código de salida es 0 (también con `-T` a secas). Solo funciona con `-T` y `</dev/null`: ahí sí aparece "PASO_DESPUES".
   - Consecuencia: se aplican las migraciones, pero la versión nueva nunca se levanta y el job marca éxito (falso positivo de despliegue; en el primer despliegue no arranca ningún contenedor).
   - Corrección sugerida: `$dc run --rm -T api node dist/migrate.js </dev/null` (o enviar el script como fichero y proteger todo comando que lea stdin), y añadir al final una comprobación de `curl -fsS https://<API_DOMAIN>/health` o `docker compose ps` para que un fallo ponga el job en rojo. Sin eso, quien tenga permiso de escritura puede lanzar `workflow_dispatch` desde una rama con un `deploy.yml` modificado y leer los secretos.
